# AI 歌舞剧教学与排演辅助系统文档评审与改进建议

> 评审对象：
>
> - `AI歌舞剧教学与排演辅助系统-需求细化文档V1.0.md`
> - `AI歌舞剧教学与排演辅助系统-技术实现落地方案V1.0.md`
> - `需求难度分析.md`
>
> 评审日期：2026 年 6 月 15 日
>
> 评审目的：从可行性、健壮性、合理性、完备性、解耦性、内聚性、耦合度、交付风险等维度，判断当前文档是否足以支撑系统开发，并提出后续需要补充和优化的方向。

## 1. 总体结论

当前三份文档已经完成了从原始设想到 MVP 方向的初步收敛，整体定位比较理性，尤其是明确把系统定位为“AI 辅助老师和编导生成初稿、整理流程、沉淀材料”，而不是“AI 全自动替代教学、创作和舞台控制”。这一点是项目能否落地的关键。

从工程角度看，当前文档已经具备以下基础：

1. 业务目标较清楚。
2. 用户角色划分基本完整。
3. 教学闭环和歌舞剧闭环已经成型。
4. MVP 优先级有初步判断。
5. 技术架构方向基本合理。
6. 对高风险需求已经做了部分降级。

但是，当前文档仍然更接近“演示型 MVP 方案”，距离可以直接指导稳定开发的“工程规格文档”还有差距。

最主要的问题是：

1. MVP 范围仍然偏大。
2. 数据模型和 API 契约不够细。
3. AI 输出格式、版本、校验和失败兜底还没有形成明确规范。
4. 视频分析、动作生成、数字人视频等增强能力仍然容易挤占主线开发时间。
5. 测试、权限、安全、部署、监控、成本评估等非功能要求不足。
6. 文档之间对算力和交付范围的口径存在不一致。

因此建议后续采用如下策略：

> 先把一期系统收敛为“文本生成 + 人工复核 + 保存版本 + Markdown 导出 + 演示兜底”的稳定闭环；视频分析、动作骨骼、数字人视频、音频处理等能力作为增强模块逐步接入，不要让它们阻塞主线交付。

## 3. 可行性分析

### 3.1 可行的部分

以下功能短期可行，适合作为一期主线：

| 功能 | 可行性 | 原因 |
|---|---|---|
| 教案生成 | 高 | 表单输入 + 大模型文本生成 + 模板导出，技术成熟 |
| 多版本教案 | 高 | 本质是提示词约束下的结构化文本生成 |
| 课堂互动脚本 | 高 | 小游戏、口令、鼓励语等文本生成稳定 |
| 剧本结构生成 | 高 | 大模型擅长结构化创作初稿 |
| 人物设定、台词、旁白 | 高 | 可以和剧本模块合并实现 |
| 分角色训练计划 | 高 | 主要是按角色维度生成训练任务表 |
| 排练复盘报告 | 高 | 基于人工观察记录生成总结报告，风险低 |
| Markdown 导出 | 高 | 后端模板拼接即可 |
| Word 导出 | 中高 | 技术可行，但需要排版调试 |

这些功能都符合当前文档中的核心定位：AI 先生成初稿，人再确认和修改。

### 3.2 中等可行但要控制范围的部分

以下功能可以做，但必须明确边界：

| 功能 | 可行性 | 建议边界 |
|---|---|---|
| 课后练习视频报告 | 中 | 先做视频质量、时长、关键帧、基础观察，不做专业判分 |
| RTMPose / MMPose 姿态提取 | 中 | 可作为技术亮点，但不保证动作正确性 |
| DTW 动作对齐 | 中 | 仅用于粗粒度参考，不输出“准确率” |
| 曲目、队形、编排辅助 | 中 | 输出建议表，不生成完整编舞 |
| 歌舞融合建议 | 中 | 输出结构化创编建议，必须由编导确认 |
| 音频裁剪和慢速排练版 | 中 | FFmpeg 可做，需限制输入格式和文件大小 |

这些能力可以增强系统亮点，但不应成为 7 月 20 日交付的硬阻塞。

### 3.3 高风险部分

以下功能短期风险较高，建议从一期主线移出：

| 功能 | 风险 | 建议 |
|---|---|---|
| Kimodo 文本到骨骼动画 | 依赖外部模型部署、生成质量和渲染链路 | 作为增强演示，不阻塞主线 |
| Wan2.2 Animate 真人 / 数字人视频 | 部署成本和生成稳定性不确定 | 放到二期或预生成展示 |
| Seedance 2.0 视频生成 | 可控性不足，动作不一定准确 | 只作为课件展示备用 |
| 专业动作纠错 | 缺标准动作库、专业评分规则、标注数据 | 一期只做辅助观察 |
| 长视频演出分析 | 算力、时长、主观评价复杂 | 改为人工观察记录 + AI 总结 |
| 舞台灯光和舞美自动控制 | 依赖现场设备和灯光协议 | 不进入本期 |

## 4. 健壮性分析

### 4.1 当前已有的健壮性设计

文档中已经体现了一些正确方向：

1. AI 结果默认是初稿，必须人工确认。
2. AI 输出失败时要保留用户输入。
3. API 不稳定时准备固定示例结果。
4. 视频分析效果一般时明确为“辅助观察”。
5. 大任务使用 Worker，不阻塞 HTTP 请求。
6. 前端通过任务状态轮询获取进度。

这些设计适合演示，也能降低 AI 不稳定带来的风险。

### 4.2 仍需补充的健壮性设计

当前文档对异常路径描述还不够细，建议补充：

| 场景 | 建议处理 |
|---|---|
| LLM 超时 | 设置超时时间、重试次数、失败提示、mock fallback |
| LLM 返回非法 JSON | 保存 raw output，尝试修复解析，失败后允许用户重新生成 |
| Worker 任务失败 | `FAILED` 状态记录错误类型、错误信息、可重试标记 |
| 用户刷新页面 | 前端可通过 taskId 和业务 id 恢复任务状态 |
| 视频上传中断 | 限制一期不做断点续传，但必须给出明确失败提示 |
| 文件过大 | 前后端同时限制，后端不能只依赖前端校验 |
| 上传格式不支持 | 后端校验 MIME、扩展名和 FFmpeg 可解析性 |
| 导出失败 | 保留报告内容，允许重新导出 |
| 权限越权 | 所有查询必须按用户角色和资源归属过滤 |
| mock 模式开启 | 页面和导出中最好标记为演示数据，避免误认为真实分析 |

### 4.3 建议增加任务状态字段

当前任务状态只有 `PENDING`、`RUNNING`、`SUCCESS`、`FAILED`、`CANCELLED`。建议在 `ai_tasks` 中补充：

| 字段 | 说明 |
|---|---|
| `id` | 任务 ID |
| `task_type` | 任务类型，如 lesson_plan、practice_report |
| `status` | 当前状态 |
| `progress` | 0-100 的粗粒度进度 |
| `business_id` | 关联课程、报告或提交记录 |
| `input_snapshot` | 创建任务时的输入快照 |
| `result_id` | 成功后关联结果 |
| `error_code` | 错误码 |
| `error_message` | 错误摘要 |
| `retry_count` | 已重试次数 |
| `max_retries` | 最大重试次数 |
| `created_by` | 创建人 |
| `created_at` | 创建时间 |
| `started_at` | 开始时间 |
| `finished_at` | 完成时间 |

## 5. 合理性分析

### 5.1 产品定位合理

文档中最合理的一点，是始终强调 AI 不是最终决策者。对于舞蹈、歌舞剧、教学评价这类强专业、强主观的场景，让 AI 直接做最终判断风险很大。

当前定位更适合真实落地：

1. AI 生成教案初稿。
2. 老师修改和确认。
3. AI 生成练习观察报告。
4. 老师复核后给学生最终反馈。
5. AI 生成剧本、角色训练、复盘报告。
6. 编导或负责人最终确认。

这条路线既能体现 AI 价值，又不会把系统推到无法保证准确性的区域。

### 5.2 技术栈选择合理

当前技术栈选择整体合理：

| 层级 | 技术 | 评价 |
|---|---|---|
| 前端 | Vue 3 + Vite + TypeScript + Element Plus | 适合表单密集型系统，开发效率高 |
| 后端 | FastAPI + Pydantic | 适合快速开发 API 和自动生成 OpenAPI 文档 |
| Worker | Celery / RQ | 适合 AI 调用、视频处理等长任务 |
| 数据库 | PostgreSQL | 适合结构化业务数据 |
| 队列和缓存 | Redis | 适合任务队列和状态缓存 |
| 对象存储 | MinIO / OSS | 适合视频、图片、导出文件 |
| 模型接入 | OpenAI-compatible SDK | 便于切换 DeepSeek、通义千问、OpenAI 等模型 |

### 5.3 排期合理性不足

当前排期比较细，但略显乐观。两人团队从 6 月 12 日到 7 月 20 日要完成：

1. 前后端工程骨架。
2. 登录权限。
3. 数据库和迁移。
4. 文件上传。
5. 异步任务。
6. LLMClient。
7. 多个提示词和 JSON 校验。
8. 教案、互动、视频打卡、报告复核。
9. 剧本、分角色训练、歌舞融合、复盘。
10. 导出。
11. 演示数据。
12. 部署和彩排。

如果再加入 RTMPose、Kimodo、Wan2.2、音频处理，风险会明显上升。

建议调整为：

| 阶段 | 优先保证 | 可选增强 |
|---|---|---|
| 第一阶段 | 项目骨架、登录、课程、LLM 生成、保存、导出 | 无 |
| 第二阶段 | 教案、互动、剧本、角色训练 | 示例素材库 |
| 第三阶段 | 学生上传、基础练习报告、老师复核 | FFmpeg 元信息和关键帧 |
| 第四阶段 | 复盘报告、演示兜底、系统联调 | 粗粒度姿态分析 |
| 第五阶段 | 演示彩排、修 bug、文档整理 | 不再加新功能 |

## 7. 解耦性分析

### 7.1 当前解耦设计较好的地方

当前架构中，以下拆分是合理的：

1. 前端只负责交互，不直接调用模型。
2. API 服务负责鉴权、数据落库、任务创建。
3. Worker 负责大模型调用和媒体处理。
4. PostgreSQL 保存结构化数据。
5. MinIO / OSS 保存视频、图片、导出文件。
6. Redis 负责任务队列和短期状态。
7. `LLMClient` 封装模型供应商。
8. `prompts/` 目录集中管理提示词。

这能避免前端、业务逻辑、模型供应商和媒体处理相互缠绕。

### 7.2 还需进一步解耦的地方

#### 7.2.1 AI 任务与业务结果解耦

建议不要让 `lesson_plans/generate` 直接同步返回最终教案。更稳的方式是：

1. API 创建业务草稿。
2. API 创建 `ai_tasks`。
3. Worker 生成结果。
4. Worker 写入结果表。
5. 前端通过 taskId 轮询。
6. 用户确认后生成 reviewed 版本。

这样可以统一处理所有 AI 长任务。

#### 7.2.2 Prompt 与代码解耦

建议每个 prompt 都有：

| 项 | 说明 |
|---|---|
| `prompt_name` | 如 lesson_plan |
| `prompt_version` | 如 v1.0 |
| `input_schema` | 输入变量要求 |
| `output_schema` | JSON Schema |
| `example_input` | 示例输入 |
| `example_output` | 示例输出 |

业务代码只关心 schema，不直接依赖提示词文本内容。

#### 7.2.3 模型供应商与业务模块解耦

建议 `LLMClient` 返回统一结果：

```json
{
  "provider": "deepseek",
  "model": "deepseek-chat",
  "raw_text": "...",
  "parsed_json": {},
  "usage": {
    "prompt_tokens": 0,
    "completion_tokens": 0
  },
  "latency_ms": 0
}
```

这样后续切换模型不会影响业务模块。

#### 7.2.4 文件存储与业务表解耦

建议建立统一 `files` 或 `media_assets` 表，所有视频、图片、导出文件都先进入统一文件表，再由业务表引用。

示例：

| 字段 | 说明 |
|---|---|
| `id` | 文件 ID |
| `owner_id` | 上传人 |
| `bucket` | 存储桶 |
| `object_key` | 对象存储 key |
| `filename` | 原文件名 |
| `mime_type` | 文件类型 |
| `size_bytes` | 文件大小 |
| `duration_seconds` | 视频/音频时长 |
| `checksum` | 文件校验 |
| `created_at` | 上传时间 |

这样 `demo_assets`、`practice_submissions`、`export_files` 都不用各自重复处理文件字段。

## 8. 内聚性分析

### 8.1 教学模块内聚性

教学模块主线是清楚的：

1. 创建课程。
2. 生成教案。
3. 生成课堂互动。
4. 管理示范材料。
5. 布置练习。
6. 学生上传视频。
7. AI 生成基础报告。
8. 老师复核。
9. 导出。

这条链路内聚性较高，适合作为系统第一主线。

建议进一步拆成：

| 子模块 | 职责 |
|---|---|
| 课程管理 | 课程基础信息、学生、老师 |
| 教案生成 | 教案 AI 生成、编辑、版本、导出 |
| 互动脚本 | 课堂互动、口令、小游戏 |
| 示范材料 | 视频、图片、动作拆解说明 |
| 练习任务 | 作业发布、提交入口 |
| 练习报告 | 视频基础分析、AI 报告、老师复核 |

### 8.2 歌舞剧模块内聚性

歌舞剧模块主线也比较清楚：

1. 创建剧目。
2. 生成剧本结构。
3. 生成人物和台词。
4. 生成分角色训练计划。
5. 生成歌舞融合建议。
6. 输入排练观察记录。
7. 生成复盘报告。

建议把 M01 和 M02 合并为一个“剧本创编”模块，因为人物、台词、旁白天然依赖剧本结构，不宜拆成太多独立页面。

### 8.3 内聚性不足的地方

以下能力目前容易跨模块扩散：

1. 示范材料。
2. 动作生成。
3. 标准动作库。
4. 学生练习视频分析。
5. 歌舞剧排练视频复盘。

这些都涉及视频、动作、素材、AI 分析。如果不收敛，很容易变成一个“媒体 AI 平台”，超出当前项目范围。

建议一期只保留：

1. 示范材料上传和动作拆解说明。
2. 学生短视频上传。
3. 基础视频观察报告。

RTMPose、DTW、Kimodo、Wan2.2 作为可拔插能力，不写死在主流程里。

## 9. 耦合度分析

### 9.1 潜在高耦合点

| 耦合点 | 风险 | 建议 |
|---|---|---|
| 业务模块直接依赖某个模型供应商 | 换模型成本高 | 统一 `LLMClient` |
| 前端直接依赖模型输出 JSON | schema 变化导致页面崩 | 后端做结构化校验和转换 |
| 练习报告强依赖标准动作库 | 没有标准动作时无法出报告 | 支持基础观察模式 |
| 导出直接依赖页面内容 | 页面变化影响导出 | 后端使用独立导出模板 |
| 文件信息分散在各业务表 | 后续维护困难 | 建统一文件表 |
| prompt 散落在代码中 | 难版本管理 | 集中 `prompts/` 并记录版本 |
| mock 数据和真实数据混用 | 演示后难清理 | 增加 `is_demo` 或环境级 mock 模式 |

### 9.2 推荐耦合控制原则

1. 前端只消费后端标准响应，不消费模型原始输出。
2. 后端只通过 `LLMClient` 调模型，不在业务代码里写供应商逻辑。
3. Worker 输出结构化结果，报告正文由模板或 LLM 生成，但必须保存原始结构。
4. 业务表保存业务状态，文件表保存文件元数据，任务表保存异步执行状态。
5. AI 输出必须经过 schema 校验后才能进入业务结果表。
6. 所有 AI 生成内容都要允许人工编辑，人工确认版本与 AI 原始版本分开保存。

## 10. 安全与隐私分析

当前文档只简单提到学生上传的视频只允许本人、老师、管理员查看。这是正确方向，但不够完整。

建议补充：

| 方面 | 建议 |
|---|---|
| 登录鉴权 | JWT + 密码哈希，禁止明文密码 |
| 资源权限 | 学生只能看自己的提交；老师只能看自己课程下的学生提交 |
| 文件访问 | 对象存储不要公开桶，使用后端签名 URL 或代理下载 |
| 导出脱敏 | 学生姓名、手机号等信息默认不出现在公开导出中 |
| 数据保留 | 明确视频保留周期，演示数据可一键清理 |
| API 密钥 | 只能放环境变量，不进入代码和 Git |
| 日志脱敏 | 日志中不打印完整 API Key、学生隐私和视频地址 |
| 演示账号 | 演示账号和真实账号分开 |

## 12. 文档之间的不一致

## 17. 最终建议

当前文档已经具备较好的产品意识和风险意识，尤其是没有盲目承诺“AI 全自动专业判分”和“全自动舞台合成”。这是非常重要的优点。

后续最关键的不是继续扩功能，而是把现有方案变得更工程化：

1. 收窄一期 MVP。
2. 细化数据模型。
3. 固化 API 契约。
4. 明确 AI 输出 schema。
5. 增加任务失败和 mock 兜底机制。
6. 补权限、安全和隐私设计。
7. 补测试计划和验收用例。
8. 统一算力、排期和交付范围口径。

建议最终一期交付口径调整为：

> AI 歌舞剧教学与排演辅助系统一期版本，重点解决老师备课、课堂互动、学生练习反馈、歌舞剧创编、分角色训练和排练复盘中的文字整理、结构生成、材料保存和导出问题。视频和动作能力作为辅助观察和演示增强，不承诺专业自动判分。

这样既能体现 AI 价值，也能保证两人团队在短周期内真实做出一个可运行、可演示、可继续迭代的系统。
