# AI 歌舞剧教学与排演辅助系统文档评审报告

> 评审日期：2026 年 6 月 15 日  
> 评审范围：`doc/` 目录下需求分析、概要设计、技术方案、难度分析、既有评审建议等文档。  
> 评审方式：只读扫描与内容分析，未对原有文档进行修改。  
> 评审目标：判断当前文档是否足以支撑详细设计、开发、测试与验收，并识别冲突、遗漏、模糊描述、重复内容和交付风险。

## 1. 总体结论

当前文档已经完成了从原始设想到演示型 MVP 的初步收敛，整体方向是合理的。文档多次强调系统定位不是“AI 全自动替代老师、编导和舞美人员”，而是通过 AI 生成初稿、整理结构、提供建议，再由老师、编导或负责人确认和修改。这一定位符合舞蹈教学和歌舞剧排演场景的专业属性，也符合短周期交付的现实约束。

从业务表达看，教学闭环和歌舞剧创编闭环已经比较清楚；从工程设计看，Vue、FastAPI、Python Worker、PostgreSQL、Redis、MinIO 的整体架构方向也基本可行；从交付策略看，文档已经识别并部分降级了舞台合成、专业动作判分、长视频分析、数字人视频等高风险内容。

但当前文档仍更接近“演示型 MVP 方案”，距离可以直接指导稳定开发的“工程规格文档”还有明显差距。主要问题包括：MVP 范围仍偏大，数据模型和 API 契约不够细，AI 输出 Schema、错误处理、权限边界、安全隐私、测试验收、部署运维等内容不足；同时，文档之间存在算力口径、优先级和交付范围的不一致。

综合判断：当前文档适合进入“范围冻结 + 详细设计补齐 + 核心闭环开发”阶段，不建议直接进入全面并行开发。建议先冻结一期范围，补齐数据模型、接口契约、权限矩阵、AI 输出 Schema 和测试用例后，再推进主线功能实现。

## 3. 优点

### 3.1 项目定位较清醒

文档多次强调 AI 不是最终决策者，AI 结果默认是“初稿”，必须支持人工修改和确认。这一点非常重要。舞蹈教学、歌舞剧创编、排练复盘都具有较强专业性和主观判断，若承诺 AI 自动完成专业判分、完整编舞或舞台控制，会显著增加交付风险。

### 3.2 业务主线基本成型

需求文档中已经形成两条主线：

1. 教学闭环：创建课程 -> 教案生成 -> 课堂互动 -> 示范材料 -> 课后练习 -> AI 观察报告 -> 老师复核 -> 导出。
2. 歌舞剧闭环：创建剧目 -> 剧本结构生成 -> 人物台词生成 -> 歌舞融合建议 -> 分角色训练 -> 排练复盘 -> 模板沉淀。

这两条主线覆盖了系统的核心价值，也便于拆分成前端页面、后端接口和 Worker 任务。

### 3.3 需求拆解较细

需求文档将教学侧拆分为 T01-T06，将歌舞剧侧拆分为 M01-M08，每个需求基本包含需求来源、使用对象、业务目标、输入内容、处理流程、输出内容、验收标准和边界说明。相比只有概念描述的需求文档，当前文档已经具备较好的讨论基础。

### 3.4 技术架构方向基本合理

技术方案选择 Vue 3、FastAPI、Python Worker、PostgreSQL、Redis、MinIO，对一个表单密集、AI 生成、文件上传和异步处理较多的系统来说是合理的。API 服务、Worker、数据库、对象存储、队列之间的职责划分也符合常见工程实践。

### 3.5 已有风险降级意识

文档已经将真实舞台灯光控制、全自动舞台合成、长视频完整分析、全自动专业动作判分等内容标记为不做或降级。这能避免项目一开始就进入高成本、高不确定性的区域。

### 3.6 演示兜底意识较强

技术方案和需求文档都提到固定演示案例、预置示例结果、mock 模式、备用截图等机制。对于 2026 年 7 月 20 日前的短周期演示交付，这类设计非常必要。

## 4. 主要问题

### 4.1 高风险问题

#### 4.1.1 MVP 范围仍然偏大

**问题描述**  
当前一期范围同时覆盖教案生成、课堂互动、示范材料、学生视频上传、练习报告、剧本生成、人物台词、分角色训练、歌舞融合、排练复盘、Markdown / Word 导出、权限、文件上传、异步任务、视频分析、可能的动作生成和音频处理。对于两人团队和 6 月 12 日到 7 月 20 日的交付周期来说，范围明显偏大。

**影响范围**  
需求、排期、开发、测试、演示稳定性。

**可能后果**  
主线功能无法打磨稳定，视频或动作增强能力挤占核心开发时间，最终交付变成多个半成品页面。

**建议改进方式**  
立即冻结一期 MVP，只保留：

- 教案生成、编辑、保存、Markdown 导出。
- 课堂互动脚本生成、编辑、保存、导出。
- 学生短视频上传。
- 基础练习观察报告、老师复核、学生查看反馈。
- 剧本结构、人物台词、分角色训练计划。
- 排练复盘报告。
- 固定案例、mock JSON、示例账号、备用截图。

将 Kimodo、RTMPose、DTW、Wan2.2、Seedance、Demucs、音频处理等全部标记为增强或预生成展示，不作为主线阻塞项。

**涉及文档或章节**  
需求文档第 7 章 MVP 功能优先级；技术方案第 8 章开发计划；既有评审第 13 章优先级调整建议。

#### 4.1.2 算力口径不一致

**问题描述**  
`需求难度分析.md` 默认团队具备 RTX 5090 级别云端 GPU；技术方案第 2.4 节写的是本机 RTX 3060 6G、R7 5800H、32G 内存，并建议长视频、批量视频、人声分离等放到云端执行。

**影响范围**  
视频分析、动作生成、音频处理、演示承诺。

**可能后果**  
需求方可能按 5090 云端能力预期功能效果，开发侧按 3060 本机能力实现，导致交付预期错位。

**建议改进方式**  
统一算力口径：

- 本地开发和演示：RTX 3060 6G。
- 文本生成：外部大模型 API。
- 视频增强：仅在云端 GPU 可用且验证通过后纳入。
- Kimodo / Wan2.2 / Demucs：未验证前只能作为预生成样例或二期能力。

**涉及文档或章节**  
`需求难度分析.md` 第 1 章；技术方案第 2.4 节；既有评审第 12.1 节。

#### 4.1.3 数据模型只有表名，缺字段级设计

**问题描述**  
技术方案列出了 `users`、`courses`、`lesson_plans`、`practice_submissions`、`practice_reports`、`musical_projects`、`ai_tasks` 等核心表，但没有字段、类型、外键、索引、状态枚举、软删除、审计字段和数据归属规则。

**影响范围**  
后端开发、数据库迁移、权限控制、测试、导出、数据一致性。

**可能后果**  
开发时靠个人理解临时设计字段，导致前后端字段不一致、数据难以关联、权限过滤困难、后续迁移成本高。

**建议改进方式**  
补充独立数据模型设计文档，至少包含：

- ER 图。
- 表结构和字段类型。
- 外键关系。
- 状态枚举。
- 索引。
- 创建人、更新人、创建时间、更新时间。
- 软删除字段。
- 文件资产统一表。
- AI 原始输出与人工确认版本的关联关系。

**涉及文档或章节**  
技术方案第 5.3 节；既有评审第 6.2、7.2.4、14.2 节。

#### 4.1.4 API 契约不足

**问题描述**  
技术方案列出了核心 API 路径，但没有请求参数、响应结构、错误码、鉴权要求、分页规则、上传协议、幂等策略和异步任务返回格式。

**影响范围**  
前后端联调、接口测试、错误处理、权限、安全。

**可能后果**  
前端和后端对同一接口理解不一致；AI 任务创建、轮询、失败重试、导出等流程容易出现返工。

**建议改进方式**  
补充 API 接口契约文档，至少覆盖：

- 请求方法和路径。
- 请求 JSON Schema。
- 响应 JSON Schema。
- 标准错误码。
- 鉴权要求。
- 资源权限校验。
- 分页、排序、过滤。
- 文件上传大小、格式、MIME 校验。
- 异步任务创建后返回 `task_id` 的统一格式。
- 重试和幂等策略。

**涉及文档或章节**  
技术方案第 5.4 节；既有评审第 6.2、14.3 节。

#### 4.1.5 “动作纠错”表述仍有误导风险

**问题描述**  
需求文档 T06 已经强调第一版不承诺逐帧精准判断动作对错，不输出“动作正确率 95%”；但技术方案仍使用“课后练习视频纠错”“规则评分”“动作对齐”等表述，容易让使用者理解为专业纠错系统。

**影响范围**  
产品预期、验收标准、用户信任、安全边界。

**可能后果**  
学生或老师误以为系统判断具有专业权威性；实际效果如果不稳定，会损害系统可信度。

**建议改进方式**  
统一命名为“课后练习辅助观察报告”。一期 UI 和文档中避免高频使用“纠错”“评分”“正确率”等词。报告结论应采用“观察建议”“拍摄质量反馈”“与参考动作存在差异”这类保守表述。

**涉及文档或章节**  
需求文档 T06；技术方案第 6.5 节；既有评审第 12.3 节。

#### 4.1.6 学生视频隐私与权限设计不足

**问题描述**  
文档只简单说明学生上传的视频只允许本人、老师和管理员查看，但没有细化资源归属、课程归属、老师可见范围、对象存储访问方式、导出脱敏、审计日志和数据保留周期。

**影响范围**  
学生视频、练习报告、导出文件、演示数据、真实数据。

**可能后果**  
出现越权访问、视频泄露、报告误导出、演示数据和真实数据混用等问题。

**建议改进方式**  
补充权限矩阵与隐私设计：

- 学生只能查看自己的提交和老师确认后的反馈。
- 老师只能查看自己课程下学生的提交。
- 管理员操作需要审计。
- 对象存储桶不公开，使用后端代理或签名 URL。
- 导出默认脱敏。
- 明确视频保留周期和删除规则。
- mock 数据增加 `is_demo` 标记或环境级隔离。

**涉及文档或章节**  
需求文档第 6.6 节；技术方案第 5.2 节；既有评审第 10 节。

### 4.2 中风险问题

#### 4.2.1 验收标准偏功能描述，难以直接测试

**问题描述**  
多数验收标准是“系统能生成”“用户可以编辑”“可以保存和导出”，缺少具体测试数据、预期结构、异常路径、权限场景和失败恢复要求。

**影响范围**  
测试设计、验收、回归测试。

**可能后果**  
验收主观化，不同人对“完整”“适合年龄段”“结构清晰”的判断不一致。

**建议改进方式**  
每个需求补充可执行验收用例，包括：

- 固定输入。
- 预期输出字段。
- 成功条件。
- 失败场景。
- 权限场景。
- 可自动化验证点。

**涉及文档或章节**  
需求文档各需求“验收标准”；既有评审第 11 章。

#### 4.2.2 AI 输出 Schema 缺失

**问题描述**  
技术方案要求每个提示词返回 JSON，并给了一个教案 JSON 示例，但没有针对每个功能给出正式 JSON Schema、版本号、示例输入输出和校验失败处理。

**影响范围**  
前端渲染、后端保存、导出模板、测试。

**可能后果**  
模型输出字段变化会导致页面展示失败、导出失败或数据无法落库。

**建议改进方式**  
补充 AI Prompt 与输出 Schema 文档：

- `prompt_name`。
- `prompt_version`。
- 输入变量。
- 输出 JSON Schema。
- 示例输入。
- 示例输出。
- 非法 JSON 修复策略。
- raw output 保存策略。

**涉及文档或章节**  
技术方案第 6.3 节；既有评审第 7.2.2、14.4 节。

#### 4.2.3 角色权限模型过粗

**问题描述**  
技术方案建议第一版只做管理员、老师/编导、学生三类角色。这有利于快速开发，但老师、编导、负责人、音乐负责人、舞美负责人之间的操作边界未说明。

**影响范围**  
课程、剧目、练习提交、报告、音频素材、导出。

**可能后果**  
上线后难以区分谁能创建剧目、谁能查看学生视频、谁能导出报告、谁能管理示范材料。

**建议改进方式**  
一期可以继续使用三类角色，但需要补充资源级权限：

- 用户与课程关系。
- 用户与剧目关系。
- 老师是否能访问全部学生。
- 编导是否能访问学生练习视频。
- 管理员操作是否需要审计。

**涉及文档或章节**  
需求文档第 2 章；技术方案第 5.2 节。

#### 4.2.4 非功能需求明显不足

**问题描述**  
需求文档中的非功能需求主要集中在可编辑、可保存、可导出、可复用、可回退、隐私与权限、演示兜底，缺少性能、并发、容量、可用性、日志、监控、告警、备份、恢复、成本、SLA 等内容。

**影响范围**  
上线运维、演示稳定性、后续扩展。

**可能后果**  
系统出现接口超时、任务积压、文件丢失、导出失败、API 费用失控时缺少应对策略。

**建议改进方式**  
补充非功能需求文档：

- 最大视频大小和并发上传数。
- AI 任务超时和重试次数。
- Worker 并发数。
- 日志字段。
- 任务监控。
- 告警规则。
- 数据备份和恢复。
- API 调用成本估算。
- 演示环境 SLA。

**涉及文档或章节**  
需求文档第 6 章；技术方案第 8.4 节。

#### 4.2.5 外部模型依赖不确定

**问题描述**  
技术方案引用 DeepSeek、通义千问、OpenAI、RTMPose、MMPose、Kimodo、Wan2.2、Seedance 2.0、Demucs 等能力，但没有明确哪些已验证、哪些只是候选、哪些需要云端环境。

**影响范围**  
技术可行性、排期、演示风险。

**可能后果**  
某个外部依赖无法部署、调用失败或效果不稳定时，直接影响演示。

**建议改进方式**  
建立外部依赖清单：

- 能力名称。
- 使用场景。
- 是否必需。
- 是否已验证。
- 部署环境。
- 成本。
- 失败兜底。
- 是否可用预生成样例替代。

**涉及文档或章节**  
技术方案第 6.1-6.8 节。

#### 4.2.6 课堂互动需求仍存在模糊描述

**问题描述**  
需求文档 T05 明确写到需求较为模糊，等待与负责人沟通，包括 AI 游戏类型、律动互动脚本定义、鼓励语音参与方式、灯光背景呈现方式等。

**影响范围**  
产品设计、前端页面、验收标准。

**可能后果**  
开发出来的课堂互动脚本不符合老师真实使用方式。

**建议改进方式**  
补充课堂互动说明：

- 互动脚本模板。
- 适用课堂环节。
- 输出长度限制。
- 是否需要语音。
- 是否需要素材关键词。
- 示例文案。
- 不同年龄段差异。

**涉及文档或章节**  
需求文档 T05。

### 4.3 低风险问题

#### 4.3.1 文档内容存在重复

**问题描述**  
需求文档、技术方案、难度分析和既有评审中都反复描述了项目定位、降级策略、优先级和交付边界。

**影响范围**  
文档维护。

**可能后果**  
后续修改时容易只更新其中一份，导致口径不一致。

**建议改进方式**  
新增一份 MVP 范围冻结说明作为唯一交付口径，其他文档引用该文档。

#### 4.3.2 术语不完全统一

**问题描述**  
文档中混用“MVP”“第一版”“一期”“本期”“增强能力”“可选增强”“演示亮点”等术语。

**影响范围**  
沟通、排期、验收。

**可能后果**  
需求方和开发方对某功能是否必须交付理解不同。

**建议改进方式**  
补充术语表，并统一交付阶段：

- 一期必做。
- 一期可选增强。
- 二期能力。
- 明确不做。
- 预生成演示。

#### 4.3.3 示例配置存在安全习惯风险

**问题描述**  
技术方案环境变量中给出默认 MinIO、PostgreSQL 密码示例。作为本地演示可以接受，但需要明确不能用于真实环境。

**影响范围**  
部署安全。

**可能后果**  
示例密码被复制到真实环境。

**建议改进方式**  
在部署文档中明确：示例密码仅本地开发使用，真实环境必须使用 `.env` 和独立密钥管理。

#### 4.3.4 原始《初步教学设想.docx》未纳入当前清单

**问题描述**  
多份文档引用《初步教学设想.docx》，但当前 `doc/` 目录下未识别到该原始文档。

**影响范围**  
需求溯源。

**可能后果**  
无法核对哪些需求来自原始设想、哪些是后续整理新增。

**建议改进方式**  
将原始文档或其摘要纳入 `doc/`，并标注需求来源、确认状态和变更记录。

## 5. 分维度评价

| 维度 | 评分 | 理由 |
|---|---:|---|
| 业务完整性 | 4.0 / 5 | 核心业务目标、用户角色、教学流程、歌舞剧流程较完整；但异常流程、边界条件、优先级冻结仍不足 |
| 需求清晰度 | 3.3 / 5 | 多数需求具备输入、流程、输出和验收；但课堂互动、动作纠错、唱段适配、音频处理仍有模糊空间 |
| 架构合理性 | 3.8 / 5 | 前端、API、Worker、数据库、队列、对象存储拆分合理；但媒体能力和 AI 任务边界还需进一步解耦 |
| 数据设计 | 2.3 / 5 | 只有核心表名，缺字段、关系、枚举、状态机、索引、审计和 ER 图 |
| 接口设计 | 2.4 / 5 | 只有 API 路径，缺请求响应、错误码、鉴权、分页、幂等、上传规则 |
| 安全与权限 | 2.2 / 5 | 有基础角色和视频可见性意识，但缺权限矩阵、数据隔离、审计、脱敏、保留周期 |
| 非功能需求 | 2.0 / 5 | 性能、并发、容量、监控、告警、备份、容灾、SLA 基本缺失 |
| 用户体验 | 3.2 / 5 | 主流程比较顺畅，强调编辑、保存、导出；但空状态、加载状态、失败状态、移动端上传体验不足 |
| 可测试性 | 2.5 / 5 | 有验收点，但缺可执行测试用例、测试数据、异常测试、权限测试和自动化策略 |
| 可交付性 | 3.0 / 5 | 文本生成类功能可交付性较好；视频、动作、音频能力会显著拉高风险 |

## 6. 关键风险清单

| 风险 | 严重程度 | 影响 | 建议处理方式 | 优先级 |
|---|---|---|---|---|
| MVP 范围过大 | 高 | 排期失控、质量下降、主线不稳 | 立即冻结一期范围，拆出增强和二期功能 | P0 |
| 数据/API 缺详细契约 | 高 | 前后端联调混乱、返工增加 | 先补数据字典和 OpenAPI 契约 | P0 |
| 视频/动作能力承诺过高 | 高 | 演示失败、用户预期错误 | 统一为辅助观察，准备预生成样例 | P0 |
| 学生视频隐私不足 | 高 | 越权访问、数据泄露 | 补权限矩阵、签名 URL、审计、脱敏 | P0 |
| 算力与外部依赖未确认 | 高 | 功能无法运行或效果不稳定 | 明确本地、云端、预生成、接口占位边界 | P1 |
| AI 输出不稳定 | 中 | 页面渲染失败、导出失败、数据不可用 | 补 JSON Schema、校验、raw output 保存和 fallback | P1 |
| 测试验收不足 | 中 | 交付不可验证、回归困难 | 补验收用例和自动化测试清单 | P1 |
| 非功能缺失 | 中 | 上线后难运维、故障难定位 | 补日志、监控、备份、任务重试、SLA | P2 |
| 术语和阶段混用 | 低 | 沟通成本增加 | 建术语表和版本范围说明 | P3 |
